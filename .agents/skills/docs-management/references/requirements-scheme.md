# 需求分层与 ID 规则

编写或变更 `docs/requirements/` 中任何条目前必读本文件。

## 需求四级分层（BABOK v3 / ISO-IEC-IEEE 29148）

| 层 | 前缀 | 定义 | 文件 |
|----|------|------|------|
| 业务需求 | `BR` | 为什么立项：降本/提效/合规等业务动机 | `business.md` |
| 干系人需求 | `UR` | 谁（boss/dev/Agent）在什么场景下要什么 | `stakeholder.md` |
| 功能需求 | `FR` | 系统必须做什么（可验收的行为） | `functional/<模块>.md` |
| 非功能需求 | `NFR` | 质量属性与约束（性能/可靠/授权/预算） | `non-functional.md` |

分层依赖方向：**BR → UR → FR**（每条下层需求必须能向上追溯到至少一条上层需求）。NFR 为横切约束，可作用于任意 FR。

## ID 编号规则

- 格式：`BR-001`、`UR-001`、`FR-<MOD>-001`、`NFR-001`
- `<MOD>` 为模块短码，3~4 位大写字母，全局唯一，注册在 `requirements/README.md`（如 `MGR`=Manager、`ENV`=环境/compose、`CI`=Jenkins、`KB`=知识库、`DOC`=文档站）
- ID **一次分配、终身不变**；条目废弃时标记 `状态: 废弃` 并注明替代 ID，**不得删除或复用编号**
- 新增条目取该前缀当前最大编号 +1；文件内按编号升序排列

## 条目写法

每条需求一个三级标题 + 固定字段（模板见 `../assets/templates/requirements.md`）：

```markdown
### FR-MGR-003 定时触发分析任务
- 状态: 生效 | 上层: UR-002 | 优先级: P1
- 描述: Manager 支持按 cron 表达式定时触发已定义的分析任务。
- 验收: 配置 `schedule_cron` 后到达时间点自动产生 task_run；手动触发与 cron 互不干扰。
```

硬性要求：

1. **可验收**：每条必须有"验收"字段，写成可观察、可判定的条件（能被脚本或人工验证），禁止"提升体验""尽量快"这类不可测表述。
2. **一条一个事实**：一条需求只描述一个行为；发现"并且/同时"连接两个行为时拆成两条。
3. **一票否决约束单列**：授权、预算、商用免费等约束写入 `non-functional.md` 并在描述中标注 `[一票否决]`，选型文档必须显式回应这些 NFR。

## 追溯矩阵（traceability.md）

格式（Markdown 表格，按需求 ID 升序）：

```markdown
| 需求 ID | 标题 | 设计章节 | 实现位置 | 验证 |
|---------|------|---------|---------|------|
| FR-MGR-003 | 定时触发分析任务 | what/manager.md §任务框架 | manager/app/scheduler.py | scripts/verify-manager.sh |
```

规则：

- 每条 FR/NFR 必须出现在矩阵中；BR/UR 可只追溯设计章节。
- "验证"列优先指向可执行脚本（`scripts/verify*.sh`），其次是人工验证步骤所在的 runbook。
- 矩阵是 Agent 做"代码↔需求 gap 分析"的输入，**必须与代码同步更新**——改代码不更新矩阵视同文档腐化。

## 与其它目录的边界

- `requirements/` 只写"要什么"，不写"怎么实现"；实现细节进 `how/`，规格契约进 `what/`。
- 其它文档引用需求时只写 ID（如"实现 FR-MGR-003"），不复制描述文本。
- 需求变更流程见 `../SKILL.md` §工作流。

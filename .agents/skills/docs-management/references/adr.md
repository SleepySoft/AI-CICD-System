# ADR 规范（docs/adr/）

在 `docs/adr/` 下新建决策记录前必读本文件。模板见 `../assets/templates/adr.md`。

## 何时必须写 ADR

满足任一条件即写：

1. 影响两个以上模块的技术选型或架构取舍；
2. 难以逆转的决定（数据模型、存储选型、协议、ID 格式）；
3. 存在被认真考虑过但最终否决的备选方案；
4. 推翻或修改 `why/` 中的既有原则。

不满足以上条件的小决策：直接写在对应设计文档的"决策与备选"表中即可。

## 编号与命名

- 文件名：`NNNN-kebab-case-标题.md`，编号 4 位全局递增（0001、0002…），先查目录取最大编号 +1。
- 编号终身不复用；推翻旧决策时新建一篇，**不改旧文内容**，只把旧文状态字段改为"已被 ADR-MMMM 推翻"。

## 状态机

```
提议 → 已接受 → （可选）已被 ADR-MMMM 推翻
```

未评审的决策保持"提议"状态；合入主线即视为"已接受"，除非显式标注待评审。

## 正文要求（四段缺一不可）

1. **背景**：只写决策时刻已知的约束与需求 ID——这是 ADR 的价值所在，禁止用事后的实现结果反填背景。
2. **决策**：一句话陈述结论。
3. **备选方案**：列出所有认真考虑过的选项及否决原因；"维持现状"若被考虑过也要列出。
4. **后果**：正面与负面都要写；列出需要同步更新的设计文档。

## 与其它文档的同步

- ADR 被接受时：同步更新 `why/` 或 `what/` 正文为**当前现状**（ADR 存历史，设计文档存现状，二者分工不重叠）。
- 设计文档中引用 ADR 用相对链接：`../adr/NNNN-标题.md`。
- 一篇 ADR 只记一个决策；一次变更含多个独立决策时拆成多篇。

# 设计文档规范（why/ / what/ / how/）

在 `docs/why/`、`docs/what/`、`docs/how/` 下新建或修改文件前必读本文件。通用规则（元信息头、归属决策顺序、单一事实源）见 `../SKILL.md`，本文件不重复。

## 三层职责边界

| 层 | 只写 | 禁止写 | 变更频率 |
|----|------|--------|---------|
| `why/` | 动机、愿景、设计原则、Non-Goals、约束背景 | 规格字段、实现细节 | 最低（推翻需 ADR） |
| `what/` | 外部可见契约：数据模型、API、配置项、行为承诺 | 内部算法、部署步骤 | 中 |
| `how/` | 内部机制：架构、流程、模块协作、部署机制 | 操作任务步骤（→ runbooks/） | 最高 |

**常见误判纠偏**：

- 在 what/ 写了"用 APScheduler 的 SQLAlchemyJobStore 实现" → 移到 how/，what/ 只留"支持 cron/interval，任务定义持久化"的行为承诺。
- 在 why/ 写了字段表 → 移到 what/；why/ 用一段话说清"为什么需要这个模型"。
- 在 how/ 写了"如何重启容器排障" → 移到 runbooks/。

## 文件组织

- **一个模块每层至多一个文件**；文件名即模块名（kebab-case），跨层命名对齐：`what/manager.md` ↔ `how/manager-architecture.md`。
- 模块清单注册在 `docs/README.md` 索引中；新增模块文件必须同步登记。
- 单文件超过约 300 行或混入第二个模块时拆分；拆分后更新索引与原文件的互链。
- 文件内章节顺序固定：WHY 摘要 → WHAT 主体/摘要 → HOW 主体/摘要（模板见 `../assets/templates/design-doc.md`）。当前层为主体，其余两层各不超过 3 行 + 链接。

## 元信息头与生命周期

```
> 版本：vX.Y · 日期：YYYY-MM-DD · 状态：草稿|生效|过时
> 定位：……（含 Non-Goals 边界）
> 关联需求：<ID 列表>
```

- 状态流转：**草稿 → 生效 → 过时**。过时文件**保留不删**，状态标注"过时"并指向替代文件——保留历史供追溯。
- 正文中引用需求一律只写 ID（如"实现 FR-MGR-003"），不复制需求文本。
- 重要选型决策：正文写当前结论 + 理由摘要，完整背景落 ADR（规则见 adr.md）。

## 图示规范

- 架构图按 **C4 层级缩放**：Context（系统与外部）→ Container（服务级，对应 compose）→ Component（模块内部）。一篇文档只画与其抽象层匹配的图。
- 图用 ASCII 或 Mermaid，保证纯文本可读；禁止只放外链图片。

## 变更同步规则

- 改 `how/` 实现机制 → 检查 `what/` 契约是否仍成立（机制变而契约不变是常态，无需动 what/）。
- 改 `what/` 契约 → 检查 `requirements/traceability.md` 对应 ID 行的"设计章节"列 → 检查 `why/` 原则是否被违反（违反则需 ADR）。
- 改 `why/` 原则 → 必须有一篇 ADR 记录变更原因。

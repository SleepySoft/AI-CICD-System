# Project Cognitive Shadow

## 1. 目标与边界

Shadow 仓是源项目的认知镜像。它保存当前需求、目标、设计、运维事实、演化原因、已验证经验、认知缺口和维护过程，不保存源码副本。

源仓是实现事实的主要来源。Shadow 仓保存稳定解释、外部契约、证据入口、影响范围和可复用判断。代码只通过源仓相对路径、符号名、测试名和提交 SHA 引用；只有解释机制必需的少量片段可以进入文档。

本文件是当前 Shadow 仓的治理规范。Project Cognitive Maintainer 每次运行前必须先读取本文件。中央模板升级不会自动覆盖本文件；Schema 和规则只能通过明确迁移流程升级，Agent 不得擅自修改 `schema_version` 或 `skill_version`。

## 2. 核心分层

Shadow 仓严格区分五类信息：

| 层 | 问题 | 权威目录 |
| --- | --- | --- |
| 当前状态 | 项目现在是什么 | `docs/` |
| 演化过程 | 项目如何变成现在这样 | `evolution/` |
| 项目经验 | 实践验证了什么 | `know-how/` |
| 认知审计 | 当前哪里漂移或缺失 | `assessments/` |
| 运行记录 | 本次检查和改动了什么 | `runs/` |

历史过程不得堆积进当前文档。当前文档服务今天的项目成员；演化、审计和运行记录服务可追溯性。

## 3. 目录职责

默认结构如下，但只有实际产生对应资产时才创建目录或文件；不得为满足模板创建空章节或空文件。

```text
shadow/
├── SKILL.md
├── README.md
├── .cognitive-state.yaml
├── templates/
├── docs/
├── evolution/
├── know-how/
├── assessments/
└── runs/
```

- `SKILL.md`：本治理规范，不写具体业务知识。
- `README.md`：人类导航入口，说明用途、源仓、状态、资产入口和阅读路径，不复制正文。
- `.cognitive-state.yaml`：机器状态，只保存 Schema、规则版本、源仓标识和最后成功维护的基线。
- `templates/`：资产初始模板。它不是权威事实；使用时复制到目标位置并填写，不得让占位符进入正式资产。
- `docs/`：当前有效文档，可按需包含 `requirements/`、`why/`、`what/`、`how/`、`adr/`、`runbooks/`。
- `evolution/`：重要认知演化；`timeline.md` 是索引，`topics/` 按稳定主题组织。
- `know-how/`：每条已验证经验一个文件，文件名使用可检索的 kebab-case。
- `assessments/current.md`：当前成立的发现；已关闭项移入 `history/`。
- `runs/`：每次维护的过程证据，不作为设计或行为的权威来源。

不得在日常维护中新增顶层分类。新资产类型必须通过 Shadow Schema 升级或明确治理决定引入。

## 4. 机器状态

`.cognitive-state.yaml` 保持简洁，基础字段见 `templates/cognitive-state.yaml`。

`source.commit` 是最后一个成功完成认知维护的源仓提交。只有全部满足以下条件后才能更新：

1. 目标提交已完成检查。
2. 需要写入的 Shadow 资产已成功落盘。
3. 索引、引用和完整性检查通过。
4. 运行记录已生成。
5. 没有导致整次维护无效的错误。

运行失败、部分失败、完整性检查失败或能力缺失导致检查不完整时，`source.commit` 不得推进。状态文件不保存分析结果、风险清单和文档索引。

## 5. 证据模型

证据按回答的问题分类，不能按固定优先级机械覆盖：

- 规范性证据：生效需求、验收标准、已批准标准、已接受决策，回答“应当做什么”。
- 实现性证据：目标提交下的代码、配置、构建定义、部署定义和依赖声明，回答“当前实现了什么”。
- 验证性证据：自动测试、CI 构建、部署结果、运行日志、监控和故障复现，回答“在哪些条件下验证过”。
- 历史性证据：Git 提交、Pull Request、Issue、评审和发布记录，回答“如何演化到这里”。
- 描述性证据：README、设计文档、操作文档和人工说明，表达已有意图但可能滞后。
- 参考性证据：既有 AI 分析、经验卡、历史运行、公司全局知识和其它项目方案，只作线索。

需求与实现冲突时记录漂移，不能让一方机械覆盖另一方。测试存在不等于测试通过；CI 无数据不等于构建正常；外部知识不能当作本项目事实。

## 6. Git 与增量发现

所有项目使用 Git。Agent 根据状态文件中的基线提交和本次目标提交自主读取 Git 历史与差异，不依赖外部注入的增量摘要。

Git 检查包括提交历史、文件增删改、重命名、配置、测试、构建部署定义和源项目文档。提交消息和 diff 只用于发现线索；最终判断必须读取目标提交下的完整当前实现、调用关系、测试和相关资产。

需要支持的边界情况：

- 无基线：执行初始化认知维护，先建立当前地图和初次审计，再记录基线。
- 正常增量：只把 diff 作为候选，不逐条翻译提交。
- 基线不可达：不得伪造连续增量；说明原因，必要时记录显式重基线。
- 浅克隆：说明历史证据受限，不得把截断历史当成完整事实。
- 历史改写：确认基线不再可靠时停止自动衔接，记录重基线和理由。
- 无新增提交：检查仍可执行，允许零资产更新。
- 源仓未提交修改：默认不进入正式资产；调用方要求检查时也必须与已提交事实分开。
- Shadow 工作树未提交修改：不得混入本次 Run；先按系统规则处理。

零产出是有效结果。没有认知变化、文档仍准确、无验证经验、证据不足或外部能力不可用时，运行记录必须说明检查范围、使用的证据和不更新原因。

## 7. 初始化

初始化由独立流程完成，完成后 Project Cognitive Maintainer 才接管日常增量维护。

初始化步骤：

1. 复制并固定当前 `SKILL.md`。
2. 创建最小 Shadow 根结构和 `.cognitive-state.yaml`。
3. 读取源仓 README、AGENTS、CONTRIBUTING 和文档规范。
4. 建立项目当前地图，提取已有文档的有效信息。
5. 用代码、配置、测试和构建定义交叉验证，不复制源项目文档。
6. 只创建有证据支撑的当前文档。
7. 建立初始认知审计。
8. 仅在有历史证据时恢复重要演化，仅在证据充分时创建经验。
9. 生成第一次运行记录。
10. 成功后记录初始源仓基线。

初始化不得为填满目录创建空资产。

## 8. 日常维护流程

按以下顺序执行：

1. **读取规范和状态**：读取源仓项目规范、本文件、`.cognitive-state.yaml`、Shadow 根索引、最近运行记录、当前审计和演化索引。
2. **发现候选变化**：检查基线到目标提交的 Git 增量。
3. **恢复当前事实**：读取候选变化在目标提交下的实现、调用方、测试、配置、构建部署定义和现有 Shadow 资产。
4. **建立证据映射**：确认预期依据、当前实现、验证证据、历史线索、已有文档和受影响资产。
5. **分类认知**：区分为新事实、事实变化、重要演化、验证经验、漂移或缺口、待确认事项、普通代码变化。
6. **维护资产**：优先更新已有文件；确有需要时创建新文件。当前结果入 `docs/`，过程入 `evolution/`，验证经验入 `know-how/`，缺口入 `assessments/`，执行过程入 `runs/`。
7. **检查全局候选**：识别公司级 Lesson Learned、Pattern、共享模块候选或标准缺口，只写入运行记录的候选建议，不自动写全局仓。
8. **执行完整性检查**：核对事实追溯、唯一权威位置、链接、索引、当前/历史分离、经验验证、审计状态和修改范围。
9. **生成运行记录并推进基线**：先完成运行记录，最后更新 `.cognitive-state.yaml`。

## 9. 当前文档

### docs/requirements/

仅在存在明确需求来源时维护。需求必须有稳定 ID、可验收要求、来源、当前状态、关联设计、实现证据和验证证据。

规则：

- 已有需求 ID 永不改号。
- 不从当前代码倒推并发明正式需求。
- 已实现行为不自动等于已批准需求。
- 提交完成不自动等于需求完成。
- 实现状态与验证状态必须分开。
- 外部需求系统存在时保存映射和必要摘要，不复制完整内容。
- 同一需求正文只保留一个权威位置。

新需求使用 `templates/requirement.md`。

### docs/why/

保存动机、目标、原则、质量属性、外部约束和 Non-Goals。不写字段规格、API 细节、算法步骤、调用关系、操作命令或单次变更历史。

### docs/what/

保存外部或跨模块可依赖的规格：边界、行为、数据模型、接口协议、配置契约、状态模型、错误语义、兼容性和外部依赖条件。只写可观察行为和稳定承诺，不写内部实现步骤。

WHAT 与 HOW 推荐按稳定主题对应，例如 `what/configuration.md` 与 `how/configuration.md`，但不要求机械一一对应。

### docs/how/

保存当前实现设计：系统地图、模块职责、依赖、关键流程、数据流、状态转换、并发和资源模型、算法、持久化、失败处理、信任边界以及构建部署结构。只有当前代码能证明的结构可写入 HOW；不能据此虚构历史决策。

### docs/adr/

ADR 只记录有证据的重大决策，包含背景、备选方案、决定、权衡、后果、状态和决策证据。当前代码只能证明现在怎样实现，不能证明当初为何这样选择；缺少历史证据时把结构写入 HOW，把原因列为待确认，不创建虚构 ADR。

ADR 原则上只增不改。决策被替代时新增 ADR，并更新旧 ADR 的状态和替代关系。新 ADR 使用 `templates/adr.md`。

### docs/runbooks/

每个 Runbook 描述一个具体操作，至少包含适用范围、前置条件、输入权限、步骤、成功验证、失败处理、回退方法和风险限制。命令、路径和配置必须能在目标提交或已验证环境中定位。未经验证的操作不得写成确定可用的正式步骤。

## 10. 演化记录

`evolution/` 记录项目如何变成当前状态，只记录认知变化，不记录普通 Git 活动。

应记录外部契约、系统边界、模块职责、核心依赖、数据模型、协议状态模型、构建测试部署前提、重要方案迁移、质量属性约束、重要假设验证或推翻，以及多个提交形成的长期方向变化。

不记录普通重命名、格式整理、无认知影响的内部重构、临时调试、机械依赖升级、逐提交摘要和原因影响都无法判断的孤立变化。

`timeline.md` 保存重要事件的简洁索引：时间或提交范围、主题、摘要、影响、详细链接和主要证据。`topics/<topic>.md` 保存连续演化，尽量说明变化前后、触发因素、已确认原因、影响、兼容性后果、关联资产和证据。

必须区分观察到的变化、已确认原因和未确认推测。推测不能写成历史事实。

## 11. 项目经验

`know-how/` 保存已经由项目事实验证且未来有助于判断或行动的经验。新经验使用 `templates/know-how.md`，每条一个文件。

可收录难以直观看出的根因、可靠诊断方法、已验证模式、迁移恢复方法、关键平台约束、决策实践后果和重复问题的判断方法。

不得收录进度、普通文件说明、显而易见语言知识、无证据建议、未确认根因、一次性细节、密钥账号或为数量生成的内容。

正式经验必须同时满足：未来可能再次遇到、能帮助判断或行动、根因或原理已确认、做法已验证、边界可说明、不与现有经验重复。已有经验优先增量更新；新证据推翻旧结论时修订当前结论，并在“演化与修订”中保留认知变化。

## 12. 认知审计

`assessments/` 保存当前发现的漂移、冲突、缺口和工程完备性问题，不保存一般代码建议或风格检查结果。

检查范围包括需求与实现、文档与实现、项目类型相关的工程完整性，以及 Shadow 资产质量。不要假设所有项目使用相同工具。

当前成立项写入 `assessments/current.md`，使用 `templates/assessment.md`。每项必须有稳定 ID、类别、严重度、状态、发现、影响、预期状态、当前事实、证据、建议动作、完成判据、首次发现和最近验证时间。

建议类别：`requirement-implementation`、`documentation-implementation`、`test-coverage`、`build-tooling`、`deployment-tooling`、`repository-structure`、`traceability`、`security-compliance`、`operational-readiness`、`knowledge-gap`。

建议严重度：`critical`、`high`、`medium`、`low`。严重度按安全、数据、交付、运行和演进影响判断，不按文字质量判断。

已解决、接受为例外或被新事实取代的发现移入 `assessments/history/`，保留原始发现、解决方式、解决证据、关闭时间和最终状态。

## 13. 运行记录

每次成功或部分执行后生成 `runs/<date>-<target-short>-<run-id>.md`，同一日期可用序号避免覆盖。新记录使用 `templates/run-record.md`。

记录至少说明基线提交、目标提交、检查范围、Git 变化、信息源、外部能力、缺失或失败能力、认知变化、Shadow 资产改动、审计项变化、经验变化、跳过候选及原因、待确认事项、全局候选、未执行检查，以及是否允许推进基线。

运行记录是过程证据，不是项目设计或行为的权威来源。

## 14. 外部组件 SKILL

运行时注入的组件 SKILL 提供 Git 之外的证据能力，例如 CI/CD、需求系统、Git 托管、部署、日志监控、制品库和公司全局知识。

规则：

- 只在确实需要某项能力时读取对应组件 SKILL。
- 不按名称猜测能力，也不无目的地加载全部组件。
- Git 已有充分证据时不重复查询外部系统。
- 能力可注入不代表一定存在数据。
- 无权限、调用失败、未配置和无数据必须分别记录。
- 外部能力失败不能解释为项目通过检查。
- 公司全局知识只能用于查重、对照和形成候选，不能证明本项目已经采用某项设计。

本 SKILL 优先依赖本地 Git 和 Shadow 资产。日报和周期报告不属于 Project Cognitive Maintainer 的职责。

## 15. 权威位置与引用

同一事实只在一个地方完整表达：

| 事实 | 权威位置 |
| --- | --- |
| 需求正文 | `docs/requirements/` |
| 当前目标和原则 | `docs/why/` |
| 当前外部契约 | `docs/what/` |
| 当前实现机制 | `docs/how/` |
| 决策历史 | `docs/adr/` |
| 操作流程 | `docs/runbooks/` |
| 演化过程 | `evolution/` |
| 实践经验 | `know-how/` |
| 当前缺口 | `assessments/` |
| 执行过程 | `runs/` |

其它文件通过需求 ID、ADR ID、审计 ID、相对链接、源仓路径、Git SHA、测试或运行 ID 引用。禁止复制需求正文、风险清单和大段设计内容到多个文件。

文件按稳定主题组织，不按临时任务、日期或单次提交碎片化。抽象层次决定目录，模块职责决定文件，日期只用于演化条目和运行记录。单篇文档跨多个稳定模块时拆分；不要为细分把完整概念拆成大量短文件。

长期文档使用最小必要元数据：`title`、`status`、`updated` 和适用的 `applies_to`。不同资产可用适合自身职责的字段，但不要添加无法验证或长期无人维护的字段。`draft` 表示证据或认可不足；`effective` 表示当前有效；`deprecated` 表示已失效但为追溯保留。

## 16. 禁止行为

- 修改源代码仓或向源仓写入 Shadow 文档。
- 复制完整源码、配置、日志或构建产物。
- 根据当前实现伪造业务需求或历史 ADR。
- 将提交活动等同于业务完成。
- 将测试存在等同于测试通过。
- 将 CI 无数据等同于构建正常。
- 将外部知识当成本项目事实。
- 将推测写入生效文档。
- 将风险清单混入设计文档。
- 将历史过程堆积在当前规格中。
- 为数量制造经验卡。
- 为满足目录模板创建空文件。
- 无关重写人工文档。
- 擅自升级 Shadow Schema。
- 自动把项目经验提升为公司级知识。
- 在维护成功前推进认知基线。

## 17. 完成标准与检查清单

一次维护只有满足以下条件才算成功：

- [ ] 已读取源仓规范和本 SKILL。
- [ ] 已确认基线与目标提交。
- [ ] 已检查 Git 增量。
- [ ] 已对候选变化恢复目标提交下的完整事实。
- [ ] 已更新受影响的认知资产，或说明零产出理由。
- [ ] 已维护必要索引和引用。
- [ ] 已检查重复事实和失效链接。
- [ ] 已更新当前审计状态。
- [ ] 已生成运行记录。
- [ ] 已记录能力缺失和未执行事项。
- [ ] 未修改允许范围之外的内容。
- [ ] `.cognitive-state.yaml` 与实际维护结果一致。

存在部分失败时，运行记录必须明确标记，且不得推进基线。

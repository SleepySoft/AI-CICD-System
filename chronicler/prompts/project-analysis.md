## 目标与边界

目标是说明项目当前真实状态、关键设计、需求覆盖和主要风险，为研发决策提供依据。

- 只分析，不修改代码仓库、shadow 仓、需求或项目文档。
- 唯一交付物是 `{{report_file}}`；不要创建 issue、知识卡片或文档草稿。
- 不以目录名称、注释或旧报告作为实现完成的充分证据。
- 不追求罗列所有文件；优先解释决定系统行为的入口、数据流、状态和边界。

## 事实优先级

发生冲突时按以下顺序判断，并在报告中指出冲突：

1. 生效的需求条目和明确验收标准：说明系统应当做什么。
2. 可执行代码、测试、配置和运行证据：说明系统现在实际做什么。
3. 正式项目文档与已接受 ADR：说明设计意图和已作决策。
4. Git 历史：辅助解释演进原因。
5. 既有报告、AI 草稿和知识条目：仅作线索，必须回到前四类来源验证。

无法验证的判断标为“待确认”，不得补全为事实。引用证据使用仓库相对路径和行号；提交证据使用完整或可定位的 SHA。

## 分析步骤

模式用于调整重点，但不改变证据标准：`full` 覆盖全部步骤；`architecture` 深入系统地图和关键流程；`requirements` 深入需求逐条核对；`compliance` 深入工程约束、安全、密钥和许可。兼容模式仍需交代其它维度是否检查，不得把未检查写成通过。

1. **建立项目地图**
   - 阅读 README、AGENTS/CONTRIBUTING、依赖清单、构建入口和主要启动入口。
   - 识别产品边界、主要模块、外部依赖、数据存储和部署单元。
2. **还原关键行为**
   - 选择 2～5 条最重要的用户或系统流程，从入口追踪到持久化/外部调用/输出。
   - 记录关键状态转换、失败路径和信任边界。
3. **核对需求与文档**
   - 若存在带稳定 ID 的需求事实源，按高优先级需求核对实现和验证证据。
   - 检查代码、需求、正式文档之间是否一致；没有需求事实源时明确说明，不自行发明需求。
4. **评估工程健康度**
   - 关注正确性、可维护性、测试与可观测性、安全/密钥、依赖许可、部署可恢复性。
   - 只报告有证据且会影响交付、运行或演进的问题；格式偏好不算风险。
5. **形成行动建议**
   - 合并同一根因导致的问题。
   - 最多给出 5 项建议，按影响和紧迫度排序，并说明验证完成的办法。

<!-- 只写有代码、测试或运行证据支撑的优势 -->

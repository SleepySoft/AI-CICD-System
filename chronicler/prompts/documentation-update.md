## 目标与边界

目标是把已验证的项目知识组织成“为什么做、对外承诺什么、内部如何实现”的稳定文档，而不是再生成一份分析报告。

- 可以读取代码仓全部内容、正式文档、Git 历史和已有分析报告。
- 只允许修改 `{{shadow_dir}}/docs/**`，并将本次更新摘要写入 `{{report_file}}`。
- 不修改源代码仓，不创建知识卡片，不把风险清单或日报混入设计文档。
- 不复制整个源码或配置；文档解释稳定契约、关键机制和证据入口。
- 保留已有正确内容和人工说明，采用增量更新；只有确定过时或重复时才删除。

## 事实与文档职责

按以下优先级取证：生效需求与验收标准 > 代码/测试/配置 > 已接受 ADR > 正式文档 > Git 历史 > 既有报告和 AI 草稿。

- **需求**记录可验收的“必须做什么”，使用稳定 ID；已有 ID 永不改号。没有明确依据时不要发明需求。
- **WHY**记录动机、目标、原则、约束和 Non-Goals，不混入字段与算法。
- **WHAT**记录外部可见规格：行为、数据模型、接口、配置和状态，不写实现步骤。
- **HOW**记录内部机制、模块协作、关键流程和技术实现，不写运维操作教程。
- **ADR**只记录有证据的重大决策及备选方案。仅从当前代码推断出的结构写入 HOW，不伪造历史 ADR。
- **Runbook**描述“如何完成一个具体操作”，必须包含前置条件、步骤、验证和回退。

若源项目已有文档规范或 AGENTS.md，优先遵循它；若没有，使用下面的默认结构。不要为了凑目录创建空文件。

## 默认文档结构

```text
docs/
├── README.md                 # 索引、状态和推荐阅读路径
├── requirements/            # 有明确需求来源时建立；稳定 ID + 追溯关系
├── why/                     # 愿景、原则、约束、Non-Goals
├── what/                    # 按业务/技术模块组织的规格与契约
├── how/                     # 与 what 模块对应的实现设计
├── adr/                     # 已知决策历史，只增不改
└── runbooks/                # 部署、操作与排障任务
```

同一事实只保留一个权威位置；其它文件通过相对链接或需求 ID 引用，不复制需求正文。文件按“抽象层次决定目录、模块职责决定文件”组织，不按临时任务或日期碎片化。

## 执行步骤

1. **发现约定**：阅读源仓和 shadow 中现有 README、文档规范、需求、ADR 与索引，确定本项目的事实源和命名习惯。
2. **建立证据映射**：将业务目标、外部契约、模块实现、运维流程分别映射到 WHY/WHAT/HOW/runbook；冲突内容列为待确认。
3. **增量维护**：先修正文档与当前代码/需求不一致的部分，再补关键缺口；避免无关重排和措辞改写。
4. **维护导航**：保证 `docs/README.md` 能定位每篇文档的用途、状态和阅读顺序；新增、移动或废弃文档时同步索引和链接。
5. **自检**：检查相对链接、重复事实、需求 ID 引用、空章节、推测语气和变更范围；确认未写出代码无法证明的行为。

## 文档质量要求

- 每篇文档开头包含版本/日期、状态（草稿/生效/过时）、定位和关联需求（适用时）。
- 关键流程优先用简洁 Mermaid 或表格表达，但正文必须在纯文本下仍可理解。
- 路径、命令、接口和配置项必须可在当前提交中定位。
- 推测内容不得进入生效文档；必要时写入“待确认事项”并说明缺失证据。
- 单篇过大或跨多个模块时按模块拆分；不要把多个层次塞进“总设计”文件。

## 目标与边界

报告用于回答“本周期发生了什么、目标推进到哪里、什么需要关注、下一步做什么”。它是事实聚合，不重新执行完整项目审计，也不修改代码、文档或知识条目。

- 唯一交付物是 `{{report_file}}`。
- 提交数、构建结果、需求状态等数字必须能说明来源和统计窗口。
- 区分“已完成”“进行中”“计划”“推测”，不得把提交活动等同于业务完成。
- 合并同一事项的代码、CI、需求与既有分析证据，避免按数据源机械堆砌。
- 缺少数据时明确写“无数据/未配置”，不要补造正常状态。

## 时间窗口

- `daily`：默认统计报告日期向前 24 小时；若补充指令指定起止时间，以指定时间为准。
- `comprehensive`：默认统计最近 7 天；若补充指令指定周期，以指定周期为准。
- 所有 Git 查询显式使用起止时间，并记录窗口；工作区未提交变更单列，不算作已完成提交。

## 数据采集顺序

1. Git 提交、diff/stat、贡献者和热点文件。
2. 同期 CI 构建与测试结果；优先使用已采集 `ci_context`，必要时使用已注入 CI 能力补充。
3. 带 ID 的需求/任务状态，以及与提交可建立的关联。
4. shadow 仓中的本周期项目分析、文档更新摘要和项目知识；它们是辅助材料，不覆盖原始证据。
5. 对关键异常回到代码、日志或构建记录验证。

## 模式要求

### daily

强调短周期变化：完成事项、变更规模、构建反馈、阻塞和下一工作日行动。控制篇幅，避免重复项目背景。

### comprehensive

强调趋势和目标：阶段成果、需求推进、质量/交付趋势、重大风险、已沉淀经验和下一周期优先级。复用已有分析结论并检查其适用提交，不重复全仓扫描。

如果 `{{task_mode}}` 不是上述值，采用 `comprehensive`，并在范围中注明回退。

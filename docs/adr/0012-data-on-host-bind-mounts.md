# ADR-0012 数据持久化：显式挂载宿主目录，升级重建不影响数据

> 日期：2026-08-26 · 状态：已接受
> 关联：what/environment.md；需求 NFR-004、NFR-006、NFR-008

## 背景

决策时刻的现状与约束：

- 环境全部持久化数据使用 Docker 命名卷（named volumes）：数据位置对宿主不透明，备份/迁移/排障都要经 `docker volume` 间接操作；`docker compose down -v` 等误操作可一键清空数据。
- 已知环境坑：WSL2 空闲回收 VM 导致容器重启（AGENTS.md），数据路径越不透明，故障面越大。
- 用户硬性要求：**所有数据显式挂载到 Docker 宿主磁盘目录；任何系统更新/升级操作都不能影响数据**。

## 决策

所有服务的持久化数据一律 **bind mount 显式落到宿主目录**（默认 `${DATA_ROOT:-./data}/<服务名>`，可在 `.env` 调整），禁止用命名卷存业务数据；升级 = 只换镜像重建容器，挂载目录不动。

## 备选方案

| 方案 | 否决原因 |
|------|---------|
| 维持命名卷 | 数据位置不透明；`down -v` 误操作即丢数据；不满足"升级不影响数据"的硬性要求 |
| 命名卷 + 定期备份脚本 | 备份是补救而非消除风险，恢复有 RPO 损失，升级窗口内数据仍可能受损 |
| 网络/分布式存储（NFS 等） | 超出现阶段规模，违背最小依赖原则（why/principles.md #2） |

## 后果

- 正面：数据位置确定，备份 = 拷贝目录，迁移 = 拷目录到新机器；升级/重建容器零数据风险；宿主上可直接查看、审计数据文件。
- 负面：需处理宿主目录属主/权限（postgres、git 等容器内 UID）；WSL 下数据目录应放 WSL 原生文件系统而非 `/mnt/c`（跨文件系统 I/O 性能差）；现存命名卷需一次性迁移。
- 同步：`docker-compose.yml` 全部命名卷改 bind mount（待实施，含迁移步骤，见 runbooks/deploy.md）；`.gitignore` 排除数据目录；NFR-008 与 traceability.md 已登记。

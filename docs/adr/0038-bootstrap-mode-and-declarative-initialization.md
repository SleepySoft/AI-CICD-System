# ADR-0038 受限引导模式与声明式组件初始化

> 日期：2026-09-03 · 状态：已接受
> 关联：[ADR-0037 初始化收归单一入口](0037-single-entry-web-init.md)；[ADR-0029 supervisor 唯一入口与 .env 前置校验](0029-supervisor-single-entry-env-prereq.md)；[ADR-0027 组件目录自包含](0027-component-directory-hooks.md)

## 背景

- ADR-0037 已决定以 Web 初始化界面取代启动、接线脚本，但 `.env` 尚不存在时 ADR-0029 会令
  `serve` 立即退出，用户无法进入负责创建 `.env` 的页面，存在引导闭环矛盾。
- 初始化同时涉及全局配置、管理员、组件选择、依赖解析、批量部署、健康等待和跨组件接线。
  若把这些逻辑分别塞入现有路由、`tools.py` 和 SPA，将形成难以测试和恢复的隐式流程。
- 组件是可选、可外置资产，核心发行包不应硬编码 Keycloak、Gitea 等组件的配置细节；组件特定
  信息仍须留在各自目录中。
- 初始化可能运行数十分钟且会被浏览器关闭、Docker 重启或网络错误中断，不能依赖进程内状态。

## 决策

新增高度内聚的 `chronicler.app.initialization` 模块：未初始化时 `serve` 进入仅提供初始化能力的
受限引导模式；初始化模块根据组件目录中的声明式 `setup.yaml` 构造依赖图和执行计划，持久化、
幂等地完成批量部署与配置，完成后关闭未认证引导面并切换到正常运行模式。

本决策对 ADR-0029 作窄化修订：**已初始化实例仍在缺少或无效 `.env` 时失败关闭；仅从未完成初始化
的实例允许使用安全默认值启动受限引导模式。**

升级时若尚无 initialization 记录但已存在 Chronicler 数据库和用户，视为旧版已投入使用实例：迁移时
直接写入“引导已关闭”记录，绝不向网络开放 bootstrap。关闭后的引导能力只能由操作者在宿主本机
执行 Chronicler 恢复子命令重新签发，不能通过 Web 端点恢复，也不能由故障自动触发。

## 备选方案

| 方案 | 否决原因 |
|------|---------|
| 先要求用户手工复制 `.env`，再打开 Web 页面 | 仍保留第二入口和易错手工步骤，无法达成 ADR-0037 的完整 Web 引导 |
| 将初始化逻辑分散进现有 auth/tools/config 路由 | 模块边界不清，状态机、权限和失败恢复难以统一测试 |
| 在核心模块中硬编码每个组件的部署顺序与接线 | 违反 ADR-0027；外置组件无法自描述，sealed 核心与组件生命周期耦合 |
| 仅保留内存中的向导进度 | 浏览器关闭或进程重启即丢失，长耗时批量部署不可恢复 |
| 初始化失败时自动删除已创建的数据 | 组件数据回滚风险高且难以保证原子性；幂等重试比破坏性回滚安全 |

## 后果

- 正面：用户获得可预检、可预览、可恢复的单一路径；组件可独立声明依赖、配置字段和检查方式；
  初始化代码、状态、API 和前端资源集中在一个模块内。
- 正面：同一执行器可在初始化完成后作为 admin 的“环境设置中心”继续用于新增组件和配置修复，
  避免再造批量部署入口。
- 负面：需新增初始化状态表、引导访问令牌、`.env` 原子写入器、依赖图执行器、日志脱敏和组件
  `setup.yaml` 契约；现有组件需逐步补齐声明或初始化 hook。
- 负面：首次写入 `.env` 后，部分进程级配置只能在重启后生效；界面必须明确展示“等待重启/继续”
  状态，并在服务恢复后自动续接，而不能伪装成已生效。
- 安全边界：未认证初始化写接口必须持有一次性引导能力；初始化完成后永久关闭，除非本机管理员
  通过显式恢复命令重新签发，不得因组件故障或 `.env` 丢失自动重开。
- 实施同步：新增 `FR-INIT-*` 与初始化 WHAT/HOW 文档；实现后更新部署 runbook、AGENTS.md 部署章节，
  并按最终清单回收旧接线脚本。

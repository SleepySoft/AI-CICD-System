# ADR-0025 组件依赖方向与能力声明：SKILL 文件存在即声明（ADR-0024 细化）

> 日期：2026-08-27 · 状态：已接受
> 关联：ADR-0024（组件即 SKILL，本篇细化其两点）；需求 FR-MGR-015、FR-MGR-016；ADR-0022

## 背景

ADR-0024 落地前的深入讨论暴露两个需要钉死的问题：

1. **依赖方向假设错误**：ADR-0024 隐含"组件 = agent 的输入资源"。实际上蒸馏/记录/报告等核心产出只依赖 harness + git + 文件系统；Outline/Qdrant/MkDocs 等是**反过来读 supervisor 输出路径**的下游消费者（"阅读工具依赖 supervisor 的输出，相当于增强"）。
2. **声明机制冗余**：讨论中曾提出给组件加 `role` 字段区分输入/输出消费，进一步收敛后发现——**SKILL 文件的存在本身就是声明**，不需要任何额外字段。

知识库的归属歧义（增强还是新能力）也在此澄清：对人（产出展示）是增强；对 agent（语义检索过往经验作为上文）是增强型新能力——缺了降级为不检索，不是缺了不能跑。

## 决策

1. **组件三分类**（语义层，不进 schema）：核心自含（harness/git/文件系统，非组件）/ 输入增强（agent 上游，缺了按 FR-MGR-016 降级）/ 输出消费（supervisor 下游读者，反向依赖）。
2. **注入规则终版**：`chronicler/skills/<组件名>/SKILL.md` 存在 → 注入 L0 摘要；不存在 → 不注入。输出消费类组件天然无 SKILL.md，supervisor 不知其存在，彻底解耦。
3. **不加 role 字段**：最多在 tools.d/ 的 yaml 注释里写一行阅读提示。
4. 知识库一体两面时拆两条目：`outline`（输出消费，无 SKILL）+ `qdrant`（输入增强，有 SKILL）。

## 备选方案

| 方案 | 否决原因 |
|------|---------|
| 组件加 role 字段显式声明方向 | 冗余：SKILL 文件存在性已完全表达该信息，双写必腐 |
| 输出消费类也注入 prompt（让 agent 知道产出会被展示） | 无收益：agent 写完报告活就干完；展示是 supervisor 与下游的事，注入只稀释注意力 |

## 后果

- 正面：schema 零新增；注入器实现极简（判文件存在）；依赖方向文档化，后续组件接入时不会再把"读者"误注进 prompt。
- 负面：无显式清单可查"谁是输出消费类"（tools.d/ 注释约定缓解）。
- 同步：docs/README.md 索引登记本篇；runner 注入逻辑按"SKILL 存在即注入"实现。

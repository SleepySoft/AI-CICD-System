# ADR-0015 备份策略：一键双模式（在线 dump+打包 / 停服整体打包）

> 日期：2026-08-26 · 状态：已接受
> 关联：需求 NFR-008、NFR-009；ADR-0012；runbooks/backup-restore.md

## 背景

ADR-0012 落地后，全部业务数据已显式落在宿主 `${DATA_ROOT:-./data}/<服务>` 目录，备份的对象边界清晰。决策时刻用户给定的约束：

- 理想：一键操作且不影响系统正常服务；次之可暂停服务，但导出要快、操作要方便。
- 复制打包文件最快，整体导出可接受；**逐条查询并手工组织不可接受**。
- Git 管理的数据层（docs/、knowledge/vault/、casc.yaml 等，ADR-0013）本身有 Git 历史与远端，不需要另行备份。

## 决策

一键双模式脚本：

- **默认在线模式**（`scripts/backup.sh`）：`pg_dumpall --clean --if-exists` 逻辑导出共享 Postgres（在线一致、不影响服务）+ 文件级 `tar` 打包其余服务数据目录。活库状态下不拷贝 postgres 原始目录（无一致性保证）。
- **`--stop` 离线模式**：停止全部运行中容器 → 整体打包 `data/`（强一致，含 postgres 原始目录）→ 自动恢复原服务。用于大版本升级前等要求强一致的场景。
- **恢复**（`scripts/restore.sh`）为离线操作：停栈 → 解包覆盖数据目录 → 有 `postgres.sql` 时灌库 → 拉起全栈。
- 备份落 `backups/<时间戳>/`（入 .gitignore），异地容灾靠人工拷贝该目录，脚本不管。

## 备选方案

| 方案 | 否决原因 |
|------|---------|
| 逐条 API/SQL 导出再手工组织 | 用户明确不可接受：慢且易漏 |
| 仅 `tar` 打包 data/（不做 dump） | 在线模式下 Postgres 活库目录拷贝不一致，恢复可能损坏；dump 是在线一致性的最低成本手段 |
| pg_basebackup + WAL 持续归档 | 物理复制 + PITR 对现阶段规模过重，运维复杂度违背最小依赖原则 |
| 第三方备份工具（restic/borg 等） | 引入新组件；增量去重需求出现时再议，当前 tar 已够用 |

## 后果

- 正面：一键、默认不影响服务；恢复路径简单（单目录解包 + 一条灌库）；Git 层零额外成本。
- 负面：在线模式文件级拷贝存在理论撕裂窗（本环境写入频率低，风险小；要强一致用 `--stop`）；备份未压缩去重、未加密，长期归档成本随数据量线性增长。
- 同步：`scripts/backup.sh` / `scripts/restore.sh`（新增）、`docs/runbooks/backup-restore.md`（新增）、`.gitignore`（排除 `backups/`）、traceability.md NFR-008 行。

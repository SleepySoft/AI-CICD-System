# AI 研发一体化环境 —— 需求分析与技术选型

> 版本：v1.0 · 日期：2026-08-21
> 目标：交付一套可一键部署的集成研发环境（WSL 镜像 / VM 镜像 / Docker 镜像 + 交互式部署脚本 + 管理界面），所有软件免费（含商用免费）。

---

## 1. 需求分析

### 1.1 功能组件拆解

| # | 功能 | 本质诉求 | 选型关键点 |
|---|------|---------|-----------|
| 1 | Git 仓库 + 管理界面 | 私有代码托管、PR/评审、Issue、Webhook、API（供 Agent 调用） | 资源占用、API 完备性、与 CI 集成 |
| 2 | CI/CD（如 Jenkins） | 流水线编译、测试、打包；触发 Agent 任务 | 插件生态、Agent/节点机制、容器化构建 |
| 3 | 开发环境 | C/C++、Android、Node.js 前后端，**可复现**的编译环境 | 必须容器化/镜像化，版本锁定 |
| 4 | 测试框架 | Python 科学计算/测试栈（"anaconda"） | ⚠️ Anaconda 授权风险（见 3.4），需替代 |
| 5 | 有头/无头浏览器 | Web UI 自动化测试、Agent 网页操作 | 无头用 Playwright；有头用 Xvfb+noVNC 远程可视 |
| 6 | Agent 预装 | 各类 AI Agent CLI、MCP 工具链、定时调度 | 免费 CLI + 自带 API Key；MCP 打通内部系统 |
| 7 | 需求管理（如 Jama） | 需求条目化、追踪矩阵、与代码/测试关联 | Jama 无开源等价物，需组合方案 |
| 8 | 知识库（向量 + Obsidian） | 语义检索（RAG）+ 人工笔记双链 | Markdown 为单一事实源，向量库做索引层 |

### 1.2 业务需求拆解（9 条 → 技术含义）

| # | 需求 | 技术含义 |
|---|------|---------|
| 1 | 统一管理代码 + CI + 测试 | Git 平台 + Webhook → CI 流水线 → 测试报告归档 |
| 2 | Agent 定时代码分析 → 结构化文档 | 调度器（cron/Jenkins）+ Agent CLI + 文档站（MkDocs） |
| 3 | Agent 比对代码与需求 → 发现 gap | 需求需**机器可读**（条目化+ID）→ 决定需求管理选型 |
| 4 | Agent 生成提交/增量报告 | Gitea API 取 commit/diff → LLM 摘要 → 报告门户 |
| 5 | Agent 辅助提取通用功能单独管理 | 交互式 Agent 会话 + 独立仓库/包注册表 |
| 6 | Agent 辅助提取知识/know-how | 交互式 Agent + 知识库写入（带人工确认环节） |
| 7 | 用户补充信息不与 AI 分析混淆 | 知识库需**来源标注**（human/ai 分区 + frontmatter 元数据） |
| 8 | 权限区分（开发 vs 老板） | 统一 SSO + RBAC；知识库/报告分级可见 |
| 9 | 编译打包保护 prompt 和流程代码 | Python 流程代码 Nuitka 编译为二进制；prompt 加密为资产文件 |

### 1.3 隐含约束

- **资源**：Android 编译是最重负载（建议 ≥16C32G，AOSP 级需更高）；决定镜像必须支持按需启停组件（profile 机制）。
- **交付形态**：三种镜像应以 **Docker Compose 为唯一事实源**，WSL/VM 镜像只是 Compose 的封装壳，避免三套维护。
- **"免费"**：须逐一核查商用授权（本设计已排除有授权风险的选项，如 Anaconda）。
- **可运维性**：部署脚本是"带交互和错误反馈的 Python 程序 + 前端管理页"——即一个**安装器 + 控制面（Control Plane）**。

```
│  调度: Jenkins 定时流水线(主) + cron(备)                         │

│  Gitea(Git+PR+Issue) │ Jenkins(CI/CD) │ OpenProject(需求管理)   │

│  Ollama(本地embedding/小模型, 可选)                             │
├──────────────────────── 构建与运行时层 ────────────────────────┤
│  toolchain-cpp │ toolchain-android │ toolchain-node │          │
│  test-python(Miniforge) │ browsers(Playwright+Xvfb+noVNC)      │
├──────────────────────── 基础设施层 ────────────────────────────┤
│  Docker Compose (profiles) —— 唯一事实源                        │
│  封装: WSL rootfs 镜像 │ VM 镜像(Packer) │ 纯 Docker 交付        │
│  安装器: aisys-installer (Python/Textual TUI + FastAPI 管理页)  │
└─────────────────────────────────────────────────────────────────┘
```

## 3. 技术选型（逐项对比 + 推荐）

### 3.1 Git 仓库与管理界面 → **Gitea**

| 候选 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **Gitea** | 极轻量（~150MB 内存）、API 完整、自带 PR/Issue/Webhook/包注册表、MIT | 无内置 CI（有 Gitea Actions 可选） | ✅ 推荐 |
| GitLab CE | 功能最全（内置 CI） | 吃资源（≥4GB 内存起步）、升级重、与你的 Jenkins 需求重叠 | 备选（若放弃 Jenkins） |
| Gogs | 更轻 | 功能与生态弱于 Gitea | 否 |

> 理由：你已指定 Jenkins 做 CI，GitLab 的内置 CI 形同虚设，白付资源成本。Gitea 的 REST API 完整，方便 Agent 读取 commit/diff/issue。自带包注册表（Maven/npm/Docker/generic）正好承接需求 5"通用功能单独管理"。

### 3.2 CI/CD → **Jenkins**（按需求指定）

- Controller + **Docker inbound agents** 架构：构建在一次性容器中执行，环境即 3.3 的工具链镜像。
- 用 **Jenkins Configuration as Code (JCasC)** 把全部配置固化进镜像，做到"开箱即用、可重建"。
- 定时 Agent 任务（需求 2/3/4）也做成 Jenkins 定时流水线，集中可见、有历史记录。
- 备选：Gitea Actions（更轻，但生态和凭据管理不如 Jenkins）。

### 3.3 开发环境 → **Docker 工具链镜像 + devcontainer 规范**

| 镜像 | 内容 |
|------|------|
| `toolchain-cpp` | gcc/clang、cmake、ninja、conan/vcpkg、ccache、gdb |
| `toolchain-android` | JDK17、Android cmdline-tools + SDK/NDK（版本锁定）、Gradle 缓存卷 |
| `toolchain-node` | Node LTS（fnm 多版本）、pnpm、yarn、playwright 依赖 |

- 全部以 Dockerfile 版本锁定，推送到 Gitea 内置 Docker registry。
- 对外同时发布 `.devcontainer` 配置，VS Code 可直接挂入同一环境，消除"我机器上能跑"。
- Android 模拟器单独一个 profile（依赖 KVM，WSL 下默认不启用）。

### 3.4 测试框架与环境 → **Miniforge（替代 Anaconda）**

> ⚠️ **授权事实（已核实）**：2024-03 起，Anaconda 公司要求 **200 人以上的组织**（含使用 Miniconda 及 defaults 通道）购买商业许可，并已实际发起诉讼/追费。Miniconda 不再是安全选项。
> ✅ **Miniforge**（社区维护、仅 conda-forge 通道）完全免费，是事实标准的 drop-in 替代。

- `test-python` 镜像：Miniforge + 预建 conda 环境（pytest、pytest-xdist、allure、robotframework、hypothesis、coverage、requests、playwright）。
- 报告用 **Allure**（免费）统一聚合，接回 Jenkins。

### 3.5 有头/无头浏览器 → **Playwright + Xvfb + noVNC**

| 模式 | 方案 |
|------|------|
| 无头 | Playwright 官方镜像（Chromium/Firefox/WebKit 三内核） |
| 有头（可视化） | 同一容器内 `Xvfb + x11vnc + noVNC`，浏览器里直接看执行过程 |
| 大规模并发（可选） | Selenium Grid（免费），默认不启用 |

- Playwright 同时是测试框架和 Agent 浏览器工具（playwright-mcp），一举两得。

### 3.6 Agent 预装与配置

- **CLI**：aider、opencode、Kimi CLI 等（工具免费，模型 API Key 由用户在安装向导中填入，存入受保护的 secret 卷）。
- **MCP 工具链**（让 Agent 能操作系统内部）：gitea-mcp（读代码/issue）、qdrant-mcp（查知识库）、playwright-mcp（浏览器）、filesystem-mcp。
- **调度**：Jenkins 定时流水线为主（有日志、可重跑、有权限控制）。
- **保密交付（需求 9）**：自研 Agent 流程（prompt + 编排代码）用 **Nuitka 编译为原生二进制**，prompt 模板加密打包为资产文件（运行时解密），Docker 镜像只含编译产物层，不含源码层。

### 3.7 需求管理 → **OpenProject（GUI）+ Sphinx-Needs（需求即代码）**

> 事实：Jama 没有开源等价物。方案分两层：

| 层 | 工具 | 作用 |
|----|------|------|
| 管理界面 | **OpenProject CE**（GPL，免费） | 需求条目、状态、看板、层级、API |
| 机器可读层 | **Sphinx-Needs**（或 doorstop） | 需求存为带 ID 的结构化文本进 Git，自动生成**需求↔代码↔测试追踪矩阵** |

- 需求 3（Agent 比对代码与需求找 gap）依赖"需求机器可读"——Sphinx-Needs 的 JSON 导出直接喂给 Agent；OpenProject 通过 API 同步。
- 若嫌重，降级方案：纯 Gitea Issue + markdown 需求模板（安装向导中可选）。

### 3.8 知识库 → **Qdrant + Obsidian Vault + Outline**

> 授权事实（已核实）：Obsidian 自 **2025-02-20 起商用免费**，可用。但它只是本地编辑器，系统侧设计如下：

| 子系统 | 选型 | 说明 |
|--------|------|------|
| 单一事实源 | **Markdown Vault（存 Gitea 仓库）** | 天然版本化、Agent 可读、用户可补充 |
| 向量检索 | **Qdrant**（Apache 2.0）+ `bge-m3` embedding（经 Ollama 本地跑） | 全文+语义双索引，供 Agent RAG |
| Web 浏览/协作 | **Outline**（自托管免费，支持 OIDC + 集合级权限） | 满足需求 8 的"老板/开发不同视图" |
| 本地编辑 | Obsidian（官方客户端，用户自选）/ Logseq（开源备选） | 直接编辑 vault 仓库 |
| 来源隔离（需求 7） | 目录约定 + frontmatter：`origin: human|ai`、`reviewed: bool` | AI 产出先入 `ai-inbox/`，人工确认后转正 |

### 3.9 门户 / SSO / 监控（横切）

| 功能 | 选型 | 理由 |
|------|------|------|
| 统一门户 | **Homepage**（或 Heimdall） | 一页聚合所有系统入口，可按组显隐 |
| SSO/权限 | **Keycloak**（OIDC） | Gitea/Jenkins/Outline/OpenProject 均支持 OIDC；建 `dev`/`boss` 两组落实需求 8 |
| 状态监控 | **Uptime Kuma** | 轻量状态页 + 告警；指标进阶可加 Prometheus（可选 profile） |
| 反向代理 | **Caddy**（自动 HTTPS，配置极简） | 统一域名入口 |

## 5. 交付形态设计

**核心原则：Docker Compose 是唯一事实源，三种镜像都是它的封装。**

```
deploy/
├── docker-compose.yml          # 核心编排（profiles: core / android / monitor / all）
├── .env.example                # 全部可调参数
├── installer/                  # aisys-installer（Python）
│   ├── tui.py                  # Textual 交互式终端向导（检测环境→收集配置→部署→验证）
│   ├── web/                    # FastAPI + 简单前端：状态仪表盘、服务启停、日志查看、健康检查
│   └── checks/                 # 每个组件的部署前检查与部署后冒烟测试（错误反馈核心）
├── images/                     # 各工具链 Dockerfile
└── packaging/
    ├── build-wsl.sh            # Compose 就绪后导出 rootfs tar，wsl --import 即用
    └── build-vm.pkr.hcl        # Packer + cloud-init 构建 VM 镜像（复用同一 compose）
```

- **安装器交互流**：环境探测（Docker/内存/磁盘/虚拟化）→ 组件勾选（profile）→ 域名/端口/管理员/LLM Key 收集 → 分步部署（每步失败给出原因与修复建议，支持断点续装）→ 冒烟测试 → 打印访问清单。
- **管理页**：服务状态、一键启停 profile、日志查看、Agent 任务历史、知识库索引状态。

## 6. 资源估算

| 场景 | CPU | 内存 | 磁盘 | 说明 |
|------|-----|------|------|------|
| 最小（core profile，无 Android 构建） | 4C | 8 GB | 60 GB | Gitea+Jenkins+Qdrant+门户 |
| 推荐（含 Node/C++ 构建、知识库全量） | 8C | 16 GB | 150 GB | 日常团队使用 |
| 完整（含 Android 编译、本地 embedding） | 16C | 32 GB+ | 300 GB+（SSD） | Android 构建是瓶颈，建议独立构建机或夜间构建 |

## 7. 实施路线（建议里程碑）

1. **M1 骨架**：compose（Gitea+Jenkins+Caddy+Keycloak）+ 安装器 TUI 最小闭环。
2. **M2 工具链**：三个构建镜像 + Miniforge 测试镜像 + Playwright + 示例流水线跑通。
3. **M3 知识与需求**：Qdrant + Outline + vault 规范 + OpenProject + Sphinx-Needs 模板。
4. **M4 Agent 层**：Agent CLI + MCP 接线 + 4 个定时任务（文档/gap/增量报告/知识提取）+ Nuitka 保密打包。
5. **M5 交付封装**：管理 Web 页 + WSL/VM 镜像构建脚本 + 验收清单。

## 8. 主要风险与对策

| 风险 | 对策 |
|------|------|
| Anaconda 类授权再变 | 关键组件固定选 OSI 许可（MIT/Apache/GPL）；安装器内置 license 清单检查 |
| Android 构建拖垮整机 | 独立 profile + 独立构建节点选项 + 资源限额（compose deploy limits） |
| Keycloak 配置复杂劝退 | 预置 realm 自动导入；提供"跳过 SSO 用各系统内置账号"降级项 |
| Agent API 费用 | 本地 Ollama 小模型兜底（embedding 已本地化）；报告类任务支持本地模型 |
| 组件过多难维护 | profile 按需启用；每组件健康检查 + Uptime Kuma 面板；镜像全部版本锁定 |

## 1. 设计原则

1. **任务即配置**：每类分析任务 = 输入采集器 + Prompt 模板 + Agent 配置 + 输出处理器，全部入库可改，同时内置一套开箱即用的模板。
2. **一切皆 Run**：每次任务执行产生一个 Run（含输入快照、Agent 日志、产出物），可回溯、可重放。
3. **人审闭环**：Agent 产出统一先落"待审区"，人工确认后才进入正式知识库/文档（呼应需求 7：不与人工信息混淆）。
4. **单容器部署**：Manager 作为 compose 中的一个服务，通过 docker.sock 拉起一次性 Agent 执行容器，不引入 K8s。
5. **最小依赖**：能用 Postgres 就不加 Redis，能用 APScheduler 就不上 Celery。

## 3. 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | **FastAPI + SQLAlchemy 2 + Alembic** | 异步、自带 OpenAPI、团队熟悉度高 |
| 调度 | **APScheduler (AsyncIO, SQLAlchemyJobStore)** | 任务定义在 DB、支持 cron/interval、无需额外中间件 |
| 前端 | **Vue 3 + Element Plus** | 中文管理后台事实标准；构建为静态文件由 FastAPI/Caddy 托管 |
| 鉴权 | **Keycloak OIDC（Authorization Code Flow）** | 复用环境 SSO；token 中的 `groups` claim 映射 dev/boss |
| 数据库 | **复用共享 Postgres，新建库 `manager`** | 不新增中间件 |
| Agent 执行 | **独立镜像 `aisystem/agent-runner`**：git + aider/opencode/Kimi CLI + MCP servers + Python 运行时 | 与 Manager 进程隔离；资源限额；凭证按需注入 |
| 实时日志 | SSE（/api/runs/{id}/logs 流式） | 比 WebSocket 简单，单向推送足够 |
| LLM 接入 | OpenAI 兼容接口抽象层（base_url/key/model 可配，默认读 .env 的 LLM_*） | 云端/本地 Ollama 可切换 |

## 4. 核心数据模型（Postgres）

```
repo_source        代码源：name, url(任意 git 远端，含 GitHub/Gitea), auth(ssh key/token 引用),
                   default_branch, sync_cron, last_synced_at, last_commit
agent_profile      Agent 配置：name, cli_type(aider|opencode|kimi|...), model, base_url,
                   api_key_ref(密钥存加密列或挂载 secret), extra_args, max_runtime_sec
prompt_template    Prompt 库：name, scope(system|task), content(支持 {{变量}}), version,
                   builtin(bool), updated_by, updated_at
task_def           任务定义：name, type(见 §5), repo_ids[], agent_id, prompt_id,
                   schedule_cron, enabled, params(JSON), output_visibility(dev|boss)
task_run           一次执行：task_id, status(queued|running|success|failed|canceled),
                   trigger(cron|manual|webhook), started_at, finished_at, input_snapshot(JSON),
                   runner_container, log_path, error, ci_context(JSON, 关联的 Jenkins 构建)
report             报告：run_id, title, type, visibility, md_path, summary, created_at,
                   reviewed(bool), reviewer
review_item        待审区条目：run_id, kind(knowhow|doc|common-module|...),
                   payload(JSON/diff), status(pending|approved|rejected), decided_by
audit_log          审计：actor, action, target, detail, at
```

要点：
- **prompt_template 版本化**：任务记录 prompt 版本，Run 可复现。
- **密钥不落明文**：`api_key_ref` 指向 Docker secret 或加密列（Fernet 对称加密，密钥来自 .env）。
- **CI 上下文入 Run**：`ci_context` 记录同期 Jenkins 构建号/结果，综合报告直接使用。

## 5. 任务类型框架（TaskType Registry）

每类任务注册四件套：`collector()`（采集输入）→ `prompt_vars()`（组装变量）→ `output_parser()`（解析产出）→ `persister()`（落库/分发）。

| 内置任务 | 输入 | 处理 | 产出 |
|---------|------|------|------|
| `code-insight`（WHY/WHAT/HOW 提取） | 仓库增量 diff + 既有 WHY/WHAT/HOW 文档（知识库 `human/`+文档站） | Agent 从代码提取/更新后端设计意图、功能、实现机制；与既有文档**逐项对比**，标注"文档缺失/代码超前/不一致" | 结构化文档草稿 → 待审区 → 确认后更新文档站 |
| `daily-report`（提交日报） | 当日 commits + diff + 关联 issue + **Jenkins 当日构建结果** | Agent 汇总功能增量、风险点、测试通过情况 | 日报（默认 boss 可见） |
| `deviation-analysis`（偏差分析） | Sphinx-Needs 需求 JSON / OpenProject 需求 + 代码 + 文档 | 需求↔实现↔文档三方比对，输出 gap 清单（含严重度） | gap 报告 + 可选自动建 Gitea issue |
| `compliance-check`（文档/脚本合规） | 文档站 + 脚本目录 + 合规规则（内置模板：目录规范/frontmatter/命名/脚本头注释等） | 逐条规则核对 | 合规报告（违规清单+整改建议） |
| `knowhow-distill`（know-how 蒸馏） | 指定 commit 区间/目录/会话上下文 | Agent 提炼可复用经验 → Markdown 卡片 | `ai-inbox/` 待审卡片 → 人审后入 `know-how/` + 重建 Qdrant 索引 |
| `comprehensive-report`（综合报告） | 上述各报告 + CI/CD 汇总 + 需求进度 | 面向老板的蒸馏周报/里程碑报告 | boss 专属报告 |

自定义任务：选 repo + 选 agent + 选/写 prompt + 定 cron，即成为一个新任务（`type=custom`）。

## 6. Agent 执行管线

```
触发(cron/手动/webhook)
  → 创建 Run(queued)，冻结输入快照(commit range、prompt 版本、CI 上下文)
  → 同步代码：git clone/pull 到缓存卷 repos/<id>/（凭证从 secret 注入，落盘前脱敏）
  → collector 采集上下文（diff/文档/需求/CI 结果），超限自动摘要分片
  → 渲染 prompt（模板变量替换）
  → docker run aisystem/agent-runner（--rm，CPU/内存限额，网络仅限内网+LLM 出口）
       env: LLM_API_KEY 等经 --env-file 注入；挂载: 仓库只读 + 输出卷可写
  → 流式回传日志(SSE)；超时/异常 → Run(failed) + 错误归因(网络/配额/解析失败)
  → output_parser 解析（约定产出为 frontmatter+Markdown，或 JSON 指令块）
  → persister：报告→reports/ 卷+元数据入库；知识卡片→ai-inbox/；索引→Qdrant
  → 通知：门户角标 + 可选 webhook（如企业微信/邮件，后置）
```

并发控制：全局信号量（默认 2 个并发 Run）+ 每仓库串行锁（避免同仓库同时分析造成 diff 基线错乱）。

## 7. CI/CD 集成（不越界、只消费）

| 方向 | 机制 |
|------|------|
| Manager ← Jenkins | 任务执行前后调 Jenkins REST（`/job/xxx/lastBuild/api/json`）拉取相关构建结果写入 `ci_context`；综合报告按时间窗聚合 |
| Manager ← Gitea | Webhook（push/merge）→ `/api/webhooks/gitea` → 触发绑定了该 repo 的任务（可配防抖） |
| Manager → CI/CD | 只读为主；`deviation-analysis` 可建 Gitea issue；不反向操控流水线 |

边界：构建、测试、发布永远走 Jenkins；Manager 不替代、只观测与综合分析。

## 8. 权限设计（呼应需求 8）

- 登录：前端跳 Keycloak；后端校验 JWT，取 `groups`。
- 角色映射：`boss`（全部可见 + 审批权 + 管理配置）、`dev`（可见 visibility=dev 的报告/文档，可触发自己权限内任务）、`admin`（平台配置）。
- 双层过滤：API 层按 `report.visibility` 过滤 + 前端路由守卫（防君子不防小人，安全以 API 为准）。
- 蒸馏报告、gap 分析、know-how 私库默认 `boss`；日报可选。
- 审计：`audit_log` 记录查看 boss 级报告、审批、配置变更。

## 11. 部署形态（并入现有 compose）

```yaml
manager:                        # 新服务，无 profile（核心成员）
  build: ./manager
  environment:                  # OIDC、DB、LLM 默认、FERNET_KEY 等
  volumes:
    - manager_data:/data        # 报告/日志
    - repos_cache:/repos        # 仓库缓存
    - /var/run/docker.sock:/var/run/docker.sock   # 拉起 agent-runner
```

Caddy 增加 `http://app.localhost → manager:8000`。

**保密打包（呼应需求 9）**：
- `agent-runner` 镜像中的任务流程代码用 **Nuitka** 编译为二进制；
- 内置 prompt 模板打包为**加密资产**（构建期加密，运行期用 FERNET_KEY 解密，密钥仅存在于 .env/secret，不进镜像层）；
- Manager 镜像多阶段构建，最终层不含源码与构建工具链。

## 13. 关键取舍说明

1. **为什么不用 Jenkins 跑这些任务**：Jenkins 适合确定性构建；分析任务需要丰富的输入编排、人审交互、报告生命周期管理，放 Manager 内聚性更好。Jenkins 结果作为输入被消费，两者互补不冲突。
2. **为什么 APScheduler 而非 Celery+Redis**：并发量小（个位数并发 Run），少一个中间件少一份运维。
3. **为什么报告落文件卷而非纯 DB**：Markdown 天然进 Git/文档站/Obsidian 生态；DB 只存元数据与索引。
4. **前端 Vue3 是上限方案**：若求快，M1-M2 可先用 FastAPI + Jinja2/htmx 出管理页，M3 再切 Vue3 静态页——接口不变。
